## 3. Database / CMS (MySQL schema + seed)

### New or evolved tables / columns (`schema.sql`)

Roughly, the schema file grew to support:

- **SEO fields** on several entities: `seo_title`, `seo_description` on (among others) `bfriends_page_headers`, `bfriends_programs`, `bfriends_events`, `bfriends_news`, philosophy sections, membership content.
- **Program “pillars” copy as a single block:** `pillars_title`, `pillars_paragraph` on `bfriends_programs` (used for the “framework” narrative on program pages instead of only a normalized pillar table).
- **Session grouping:** new table **`bfriends_program_session_types`** (per program: type title + sort order). **`bfriends_program_sessions`** gained **`session_type_id`** (nullable FK) so sessions can be grouped (e.g. “Facial” vs “Scalp”) for display and admin editing.
- **Process steps scoped by page:** `bfriends_process_steps` includes **`page_key`** so the same step model can serve **home** vs **customer journey** without mixing rows.
- **Why cards:** optional **`hidden_in_home`** so a card can exist for About but be hidden on the homepage carousel/list.
- **Philosophy content helpers:** tables for **`bfriends_core_beliefs`** and **`bfriends_ecosystem_items`** (with seed examples for ecosystem names, blurbs, and URLs).

**Practical note:** `schema.sql` is written as a mix of `CREATE TABLE IF NOT EXISTS` and repeated `ALTER TABLE` lines. On a brand-new database that is fine if you run the file once; on an existing DB you may need to run only the *new* alters or maintain a migration tool—your friend may already have a preferred workflow.

### Seed data (`seed.sql`)

- Updated to populate new columns and the **session type + grouped sessions** shape where programs need it.
- Aligns sample content with the new program page layout expectations (pillars title/paragraph, grouped sessions, etc.).

## 4. Server-side CMS reads (`lib/cms.ts`)

This file is the **read path** from Next.js server components / route handlers into MySQL.

Notable behaviors added or refined:

- **`getWhyCards(includeHiddenInHome)`** — homepage passes `false` so cards with `hidden_in_home` are excluded; About can pass `true` to show the full set. Includes a fallback query if the column does not exist yet (older DB).
- **`getProcessSteps(pageKey)`** — loads steps (and nested subpoints) for **`home`** or **`customer-journey`**, with backward compatibility if `page_key` is missing.
- **`getProgramBySlug`** — loads sessions; if session types exist, builds **`sessionGroups`** via `buildSessionGroupsPublic`; otherwise falls back to a single default group **“Signature Sessions”** so the UI always has a stable shape.
- **Field aliasing** for camelCase UI: `button_label` → `buttonLabel`, image fields, `pillars_title` / `pillars_paragraph`, prev/next program slugs, etc.
- **`getPageSeo(pageKey)`** — central place for `<title>` and meta description for keys like `home`, `philosophy`, `customer-journey`.
- **`getCoreBeliefs()` / `getEcosystemItems()`** — feed the redesigned About/philosophy sections.
- **`getSiteSettings()`** — key/value map from `bfriends_site_settings` with defaults for site name and contact info if the table/query fails.

## 5. Admin API and program editor (backend surface you “vibe checked”)

### Shared persistence helper (`lib/admin-program-children.ts`)

**Untracked in git at write time** but **imported by production code** (`lib/cms.ts`, admin routes): this module is important to commit.

It provides:

- **`replaceProgramChildren(connection, programId, steps, session_types?, legacySessions?)`** — inside a transaction, deletes and re-inserts program steps, session types, and sessions. Accepts either nested **`session_types`** or legacy flat **`sessions`** (wrapped as a single type “Signature Sessions”).
- **`buildSessionTypesForAdmin`** — nests DB rows for the admin JSON shape.

### REST handlers under `app/api/admin/programs/`

- **`[id]/route.ts` (GET/PUT):** GET returns the program plus `steps`, `pillars`, `sessions`, and nested **`session_types`**. PUT updates the program row (including **SEO** and **pillars_title / pillars_paragraph**) and calls **`replaceProgramChildren`** so child tables stay consistent.
- **List/create route and sessions sub-routes** were adjusted in line with the new model (sorting, session type linkage, etc.—see git diff for exact SQL and field lists).
- **`app/api/admin/seed/route.ts`** — touched to stay compatible with the richer program/session model (re-seed or dev bootstrap—verify auth before exposing in production).

### Admin UI (`app/admin/programs/[id]/page.tsx`)

### Types (`lib/types-admin.ts`)

## 6. Public program pages — layout, data, and “how it should be”

This section is intentionally detailed so you can see **what actually renders today**, **where each line of copy and image comes from**, and **what you still need to fill in (or code) for the page to feel complete**.

### 6.1 Page shell (`app/programs/[slug]/page.tsx`)

- **`generateStaticParams`** (plus `dynamic`) — program URLs are built from **`getProgramSlugs()`** (database when available).
- **`<PageHeader variant="programs" />`** — hero band **above** the scrollable program body:
  - **Title:** `program.name` (display name, e.g. “Fitness”), not the long marketing `title` field.
  - **Image:** `program.image`, falling back to `"/images/hero-test.png"` if missing.
  - **Primary action:** “Book Now” → **`BOOK_NOW_URL`** (same external booking link as elsewhere).
- **`generateMetadata`** — `<title>` / description / Open Graph use **`seo_title` / `seo_description`** when set on the program row; otherwise it falls back to `philosophy`, then `title`, then a generic sentence. OG image uses `program.image` when present.
- **`<ProgramContent program={...} programs={...} />`** — receives the **full program object** from `getProgramBySlug` plus the **list of all programs** (for prev/next resolution only).

So: the **header** is “brand + program name + book”; the **body** below is everything in `ProgramContent`.

### 6.2 Body structure — what appears, in order (`ProgramContent.tsx`)

Everything below is inside **`ProgramContent.module.css`** (large editorial layout: full-bleed sections, grids, motion, prev/next panels).

1. **The Philosophy** (optional block)  
   - **Renders only if** `program.philosophy` is a non-empty string.  
   - Fixed section heading in the UI: **“The Philosophy”** (not configurable from CMS).  
   - Body is the **single `philosophy` text** from the program row as returned by **`getProgramBySlug`** (this component does **not** merge `programs-data.ts` for philosophy—only the framework fields use static fallback; see §6.3).

2. **The Framework** (always shown)  
   - Eyebrow in UI: **`02 / The Framework`** (hardcoded label, not from DB).  
   - **Left / layout:** large **image** with a scroll-based reveal (IntersectionObserver toggles visibility class on the image wrapper).  
   - **Copy:** two-column block: **headline** + **paragraph** (see resolution ladder in §6.3).  
   - Visually aligned with the “home intro” style (image + split title/body), but copy is program-specific.

3. **Signature Sessions** (optional block)  
   - **Renders only if** there is at least one session after resolving groups (§6.4).  
   - Section eyebrow in UI is always the string **`Signature Sessions`** — even when you have multiple **sub-groups** with their own titles (see below).  
   - **Per-group heading (`<h3>`):** shown when:
     - there is **more than one** session group, **or**
     - the single group’s `typeTitle` is set and is **not** exactly `"Signature Sessions"`.  
   - So: one flat list from the DB still reads as one grid with **no** sub-heading; multiple types (e.g. “Facial”, “Scalp”) get **sub-headings** above each grid.  
   - Each **card:** image (`session.image` or **fallback** to `program.image`), **title**, **description**. Staggered **Framer Motion** entrance when the section enters view.

4. **Get started** (always shown)  
   - Heading: **“Ready to experience {program.name}?”**  
   - Button: **“Book a session”** → same **`BOOK_NOW_URL`** as the header (intentional duplicate CTA).

5. **Previous / Next program** (optional strip)  
   - **Renders only if** `previousProgram` and/or `nextProgram` **slugs** are set on the program.  
   - Resolves **names and background images** by looking up those slugs in the **`programs`** array passed from the server (all active programs).  
   - If a slug does not match any row, that side renders as an **empty placeholder** (layout gap).  
   - Commented-out code suggests an “Explore Programs” eyebrow above this strip may return later.

**Important:** In the current `ProgramContent.tsx` there is **no** dedicated block for **`quote`**, **`steps`** (Find / Fit / Flow), **`programItems`** (icons list), or **`breadcrumb`** — those fields still exist on **`ProgramData`** / in the DB in places, but **they are not read by this component**. If you expect visitors to see the three-step “framework” ladder or opening quote, that content must either live inside **`philosophy`** / **`pillars_paragraph`** copy for now, or the UI needs to be extended again.

### 6.3 Framework copy and image — resolution order (“where does this text come from?”)

**Title + paragraph (what the UI calls the framework conclusion):**

1. **Database:** `pillars_title` and `pillars_paragraph` (trimmed) on the program row — **preferred** when both CMS fields are used.  
2. Else **static file:** `lib/programs-data.ts` entry whose **`slug`** matches the current program (case-insensitive) — uses that row’s **`pillarsTitle` / `pillarsParagraph`** if set.  
3. Else **built-in fallback** in code: title **“The Framework”** and a short generic BFriends paragraph (`FRAMEWORK_FALLBACK_*` constants).

**Framework hero image:**

1. `pillars_image` from DB (mapped to `pillarsImage` on the client object).  
2. Else **`program.image`** (main program card / header image).  
3. Else static **`programsData`** match for **`pillarsImage`** or **`image`**.  
4. Else **`/images/hero-test.png`**.

So for a polished page **without** relying on static `programs-data.ts`, you should set in the admin/CMS at minimum: **`pillars_title`**, **`pillars_paragraph`**, and ideally **`pillars_image`** (or a strong **`image`** used everywhere).

### 6.4 Sessions — resolution order (`getSessionGroups` in component + `getProgramBySlug` in `lib/cms.ts`)

**On the server (`getProgramBySlug`):**

- If **`bfriends_program_session_types`** + linked sessions work: builds **`sessionGroups`** as `{ typeTitle, sessions: [{ title, description, image }] }[]`.  
- If that path errors (older DB): loads flat **`sessions`** only; the UI still works.

**On the client (`getSessionGroups` in `ProgramContent.tsx`):**

1. If `program.sessionGroups` is a **non-empty array** → use it as-is.  
2. Else if `program.sessions` is non-empty → **one** synthetic group: **`typeTitle: "Signature Sessions"`** with those rows.  
3. Else → no sessions section (entire block omitted).

**Session card image:** each row’s **`image`**; if missing, the card uses **`program.image`** as fallback so cards are never imageless if the program has a hero image.

**How it should be for editors:**  
- Use **session types** when a program has natural chapters (e.g. different treatment families). Titles become the **`<h3>`** group labels.  
- Use **one** type named “Signature Sessions” if you want a **single grid with no sub-heading** (because the UI suppresses redundant group titles in that case).  
- Always add **per-session images** in admin when you can; otherwise the UI repeats the program hero image, which is acceptable but less rich.

### 6.5 Styling (`ProgramContent.module.css`) — what “current” means visually

- **Philosophy** — centered / editorial column, strong typographic hierarchy.  
- **Framework** — full-width section, large imagery, eyebrow, split title + body, motion on scroll.  
- **Sessions** — responsive **grid of cards** (image on top or side depending on breakpoint), group titles when applicable, consistent spacing with the rest of the site.  
- **CTA** — simple band with primary button.  
- **Prev/Next** — large **clickable panels** with background image, overlay, and chevron affordances.

Exact breakpoints and tokens live in the CSS file; the intent is a **calm, magazine-like** program story: philosophy → framework story → concrete offerings → book → explore sibling programs.

### 6.6 `lib/programs-data.ts` — types vs UI

- **`ProgramSession` / `ProgramSessionGroup` / `sessionGroups`** — match what **`ProgramContent`** consumes.  
- **`pillarsTitle` / `pillarsParagraph`** — mirror DB columns for static fallback and tooling.  
- **`pillars`** (array of `{ title, description }`) and **`frameworkFromPillars()`** — useful when generating paragraph copy from structured pillars; **the live program page does not render the pillar list as separate cards** today.  
- **Legacy `programItems` (with Lucide-style `icon` names)** — not used on this page anymore; session cards are **image + text** only.

### 6.7 How it should be — content & CMS checklist (goal state)

| Goal | What to do |
|------|----------------|
| Page reads uniquely per program | Fill **`philosophy`**, **`pillars_title`**, **`pillars_paragraph`**, **`pillars_image`** (or rely on a strong **`image`**) in admin for each program. |
| Sessions look intentional | Add **session types** when there are multiple categories; add **session images** for each row. |
| SEO / sharing | Set **`seo_title`** and **`seo_description`** per program; keep **`image`** valid URLs (R2 or allowed host). |
| Prev/next navigation | Set **`previous_program`** / **`next_program`** to **slugs** that exist on other active programs (typos → empty panel). |
| Do not depend on code fallbacks | Treat **`programs-data.ts`** as backup / dev reference; production truth should be **DB**. |

### 6.8 How it should be — product / engineering (if you extend the page again)

- **Re-introduce `quote`** as its own band if marketing wants a pull-quote above philosophy.  
- **Re-introduce `steps`** (numbered Find / Fit / Flow) if the framework section should show **structured steps** in addition to the long **pillars** paragraph.  
- **Surface `breadcrumb`** in the header or under the title if IA needs “Programs / Fitness” style orientation (currently unused in `ProgramContent`).  
- **Align section eyebrow** (`02 / The Framework`, `Signature Sessions`) with CMS if you ever want localized or program-specific labels (today they are mostly fixed English strings in code).
